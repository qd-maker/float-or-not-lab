# 「浮不浮实验室」七日最终复盘

项目周期：Day1 到 Day7
最终 Demo：[https://float.heyqi.xyz/](https://float.heyqi.xyz/)
GitHub：[qd-maker/float-or-not-lab](https://github.com/qd-maker/float-or-not-lab)

## 1. AI 真正帮上忙的地方

### 1.1 加快从模糊需求到可执行任务的过程

最初只有「做一个单一知识点科普小工具」这一要求。AI 帮我把它拆成了可以逐日交付的路径：

```text
概念实验 → 公式计算 → 真实题训练 → 错因诊断
→ AI 讲解 → 同类强化 → 学习反馈
```

它还帮助我先定义 API Contract，再实现 FastAPI 接口、Pydantic 模型和 React 页面，减少了边写边改接口的成本。

### 1.2 快速提供工程初稿

AI 对以下工作帮助明显：

- FastAPI 和 React 项目骨架。
- 三类浮力公式的请求、响应和分步解析结构。
- 10 道题的初稿以及常见错因分类。
- SSE 流式输出、Markdown 与 KaTeX 数学公式渲染。
- LocalStorage 学习记录迁移、错题本和订正状态。
- AI 变式题的 Prompt、Pydantic 校验和本地降级题。
- 测试用例、部署文档和演示脚本初稿。

这些内容并不是直接复制后就结束，而是让我更快得到一个可以验证的版本，再根据真实页面和业务逻辑继续修正。

### 1.3 辅助 Debug 和回归验证

AI 不只用于生成代码，也用于定位具体问题。例如：

- 找出 CSS Grid 的最小内容宽度导致 390px 页面被撑到 643px。
- 将网格列修正为 `minmax(0, 1fr)`，并给子项补充 `min-width: 0`。
- 发现题库导航、答题区和 AI 小老师形成三列后，正文宽度过窄。
- 使用浏览器自动化检查 1440px、1024px 和 390px 布局及横向溢出。
- 检查 AI 回答是否真的产生多个 SSE 分片，以及 KaTeX 节点是否成功渲染。

AI 最大的价值不是替我完成整个项目，而是缩短「提出方案、做出版本、发现问题、再次迭代」这个循环。

## 2. AI 出错最多的地方

### 2.1 业务和学科理解不够稳定

AI 最初把实验写成直接比较「物体重量」和「排开水重量」，没有明确这是物体完全浸没时的最大浮力。若不补充这个条件，会与最终漂浮时 `F浮 = G物` 产生概念冲突。

修正方式：明确实验场景，并区分「刚完全浸没时的运动趋势」和「最终漂浮后的平衡状态」。

### 2.2 容易给出泛化而不精准的解释

学生在潜水艇题中选错具体选项后，AI 曾经把选项解释成题目中没有出现的「改变水的密度」。

修正方式：把题干、全部选项原文、学生选项文本、正确选项文本、标准解析和错因提示一起传入，并要求 AI 必须点名具体干扰项。

### 2.3 容易忽略统计口径

AI 最初把「提交次数」当成「完成题数」，也把所有曾经答错的题永久算作待订正。生成题加入后，还可能让基础题进度出现 `11/10`。

修正方式：分开记录提交次数、不同基础题完成数、最近结果、是否曾经答错和是否为强化题。

### 2.4 容易为了功能完整而牺牲界面可读性

早期布局把题库、答题解析和 AI 小老师同时放成三列，功能都在，但文字被限制在窄列里。概念实验的结论区也曾只放在右侧，造成左下方像缺了一块。

修正方式：通过真实截图而不是只看代码判断布局；题库保留窄导航，答题区恢复宽主栏，AI 区放到下方；实验结论横跨输入区和水槽区。

### 2.5 生成式内容不能直接作为确定性规则

AI 生成的变式题即使是合法 JSON，也可能超纲、照抄原题、答案不在选项中或解析为空。

修正方式：采用以下保护链路：

```text
受限 Prompt
→ Pydantic 校验
→ 业务规则校验
→ 确定性代码判题
→ 任意失败时使用本地降级题
```

## 3. 如果重来，我会怎么做

1. **先定义验收路径。** Day1 就写出 5 条核心用户路径，而不是先堆页面：看懂浮沉、算出浮力、完成一道题、订正错题、AI 不可用时仍能继续。
2. **更早定义数据语义。** 一开始就区分提交次数、完成题数、错题和订正状态，避免 Day5 再迁移统计结构。
3. **先做纵向切片。** 先完成「一个实验 + 一个公式 + 一道题 + 一次 AI 降级」的完整闭环，再扩展到三种公式和十道题。
4. **更早进行真实视觉验证。** 每天固定检查桌面、平板和手机三种尺寸，不等到功能增加后再处理嵌套网格。
5. **把确定性逻辑和生成式能力从第一天就分开。** 公式计算、标准答案和判题永远由代码负责，AI 只负责解释和生成候选内容。
6. **更早邀请目标用户试用。** 至少找 1 到 3 名初中生或老师完成演示路径，观察他们是否真的理解，而不只验证页面能运行。
7. **部署前置。** Day2 或 Day3 就建立测试环境和自动部署，后续每天直接验证线上版本。

## 4. 对七日协作流程的三个回答

### 4.1 这七天里，流程设计得比较好的地方是什么？

我认为最好的地方有三点：

- 前四天目标明确，要求每天都有可见产出，避免一直停留在规划阶段。
- 强调 AI 协作过程而不是只看最终成品，促使我记录 AI 的错误、判断和修正过程。
- Day5 到 Day7 允许自主选择方向，使我可以基于前四天真实暴露的问题继续深化，而不是为了形式重新开一个项目。

这种安排既有范围约束，也保留了后半程的自主性，比较接近真实产品迭代。

### 4.2 如果让我改进这套流程，我会先改哪里？

我会优先增加一次中途的目标用户反馈，例如 Day3 或 Day4 让一名学生、老师或评审实际操作 10 分钟，再根据观察决定后续方向。

当前流程能很好地验证交付能力，但主要反馈来自开发者和 AI。加入一次真实用户观察后，可以更早发现「功能能跑但学生不一定看得懂」的问题，也能让 Day5 到 Day7 的自主迭代更有数据依据。

### 4.3 我是否愿意继续投入后续协作，为什么？

愿意。

这七天的工作方式与我希望发展的方向一致：不是只写一个孤立接口，也不是只调用一次模型，而是把需求分析、前后端实现、AI 边界、测试、部署和产品体验连成完整交付。

我也希望继续在真实反馈中提升两项能力：一是把 AI 能力放进稳定的工程约束中，二是用可验证的用户结果判断功能是否真正有价值。

## 5. 最终结论

这次项目让我形成了一个更明确的 AI 协作原则：

> AI 负责加速探索和实现，人负责定义目标、验证事实、处理边界并对最终结果负责。

项目最终完成的并不是一个通用聊天机器人，而是一条围绕浮力知识点的可运行学习闭环：

```text
看见现象 → 学会公式 → 完成题目 → 识别错因
→ 获得针对性讲解 → 再练一道 → 查看进步
```
